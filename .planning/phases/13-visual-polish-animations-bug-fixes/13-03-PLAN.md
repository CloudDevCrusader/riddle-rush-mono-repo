**Step 1: Write a reproducing unit test FIRST**

In `useGameActions.spec.ts`, add a test case (or test block) that:

1. Sets up a game session with exactly 2 players
2. Simulates round 1: Player 1 submits answer, then Player 2 submits answer
3. Asserts that `allPlayersSubmitted` returns `true` ONLY after both players submit
4. Asserts that `getCurrentPlayerTurn()` returns Player 1 first, then Player 2 after Player 1 submits
5. Simulates the round transition (completeRound / startNextRound)
6. Asserts that in round 2, Player 1 gets a turn again (round state properly reset)

Run the test. If it fails, the bug is reproduced. If it passes, the logic is correct at the unit level and the bug may be in the page-level interaction.

**Step 2: Investigate root cause**

Based on the research, likely causes are:

- `resetPlayerRoundState()` timing issue during round transitions — if `hasSubmitted` is reset before the UI checks `allPlayersSubmitted`, the last submission could appear "not submitted"
- The `submitAnswer()` flow in the game page may check `allPlayersSubmitted` with stale state
- Race condition between `submitPlayerAnswer` action and `allPlayersSubmitted` getter reactivity

Trace the flow:

1. Read `useGameActions.ts` — find `submitAnswer` or `submitPlayerAnswer`
2. Read `usePlayerManager.ts` — find `allPlayersSubmitted`, `getCurrentPlayerTurn`, `resetPlayerRoundState`
3. Check if `allPlayersSubmitted` check happens synchronously after the submission mutation
4. Check if `startNextRound` or `completeRound` resets player state at the right time

**Step 3: Apply fix**

Based on root cause analysis, apply the minimal fix. Common fixes:

- Ensure `allPlayersSubmitted` is checked synchronously after setting `hasSubmitted = true`
- Ensure `resetPlayerRoundState()` is NOT called before the round completion check
- If there's a `nextTick` or async gap, make the check synchronous

Update the test to verify the fix. Run `pnpm run test:unit` from `apps/game/` to confirm all tests pass.

**Important:** If after investigation the bug is NOT reproducible at the unit level (test passes without changes), document this finding. The bug may only occur in the actual UI interaction flow — in that case, add defensive guards (e.g., a guard in `startNextRound` that verifies all players have actually submitted before transitioning) and note that E2E testing is needed to fully verify.
